📦 14 个核心技能

类别技能名触发场景核心行为
入口 using-superpowers 每次会话启动 检测任务类型 → 自动路由到对应技能；1% 概率也检查
设计 brainstorming 需求模糊、需要方案 苏格拉底式追问 → 2-3 备选方案 → 分块审批 spec
规划 writing-plans spec 就绪后 拆成 2-5 分钟粒度任务，精确到文件路径+验证命令
执行 subagent-driven-development 有子 agent 能力时 每个任务 = 独立子 agent → spec 合规审查 → 代码质量审查
执行 executing-plans 无子 agent 能力时 顺序执行 + 检查点 + 随时可停下来继续
执行 dispatching-parallel-agents 多独立问题域 并发子 agent，互不干扰的问题同时推进
质量 test-driven-development 任何代码修改 严格 RED→GREEN→REFACTOR，禁止跳过红灯写代码
质量 systematic-debugging 遇到 bug 4 阶段：调查 → 模式分析 → 假设 → 修复（非随手改）
质量 verification-before-completion 宣布"完成"前 必须跑全新验证 + 贴完整输出，没证据不算完成
质量 requesting-code-review 任务间 按严重程度的结构化自审查，严重问题阻止继续
质量 receiving-code-review 收到外部 review 技术性回应每条反馈，有依据可反驳
环境 using-git-worktrees 开始开发前 每个特性独立 worktree，隔离环境+基线验证
环境 finishing-a-development-branch 开发完成 验证 → 决定合并/PR/保留/丢弃 → 清理
扩展 writing-skills 要创建新技能 TDD 写文档——先写不完整的 SKILL.md 看 agent 哪里犯错→迭代

⚖️ 六条铁律（Iron Laws）

铁律 01
设计先于编码
没有 approved spec，不动手写代码。brainstorming 阶段必须产出结构化设计文档并获用户确认。
铁律 02
TDD 优先
没有失败的测试，不写生产代码。严格 RED → GREEN → REFACTOR 循环，禁止跳过红灯。
铁律 03
系统化而非随缘
bug 修复必须走四阶段根因分析（调查→模式→假设→修复），禁止"随手改了试试"。
铁律 04
证据胜于声称
宣布"完成"前必须跑全新验证并贴完整输出。没有客观证据 = 没有完成。
铁律 05
子 agent 审查门槛
每个任务完成后：spec 合规审查 → 代码质量审查。两道门槛都过才能进入下一个任务。
铁律 06
YAGNI + DRY
你不需要它（You Aren't Gonna Need It）。不重复自己（Don't Repeat Yourself）。简单是首要目标。

📊 有没有 Superpowers 的区别

❌ 不用 Superpowers

  • 你说"加个功能"，AI 直接写代码
  • 没有 spec，边写边猜你的意图
  • 写完就完了，不验证不审查
  • 代码风格每次可能不同
  • bug 修复 = 随手改改试试
  • 大功能一个 agent 硬扛到底
  • 你靠人力 review 找问题

✅ 用 Superpowers

  • 你说"加个功能"，AI 先追问细节 → 出 spec
  • spec 分块让你审批，确保理解正确
  • 拆任务 → 独立子 agent → 双审查 → TDD
  • 代码风格受审查门槛约束，一致性高
  • bug 修复 = 根因分析 → 复现测试 → 修复 → 验证
  • 大功能自动拆成并行/串行子任务
  • AI 自己 review 自己，你只看最终结果
